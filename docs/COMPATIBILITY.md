# Mod 与游戏版本兼容性 —— 设计笔记（讨论稿）

> 状态：**待讨论**（2026-09-30 起）。等与朋友、站长商议后再决定做多少。
> 本文记录：现状实测数据、可用的信号源、推荐方案，以及需要大家一起定的问题。

---

## 1. 问题是什么

AMM 想告诉用户一句话：「**这个 mod 在你当前的游戏版本上能不能用**」。

现在只有一条依据：`Info.json` 里的 `GameVersion` 字段（UMM 标准字段）。

**实测数据（我的机器，11 个已安装 mod）：声明了该字段的 = `0` 个。**

| 检查项 | 结果 |
|---|---|
| 11 个已安装 mod 中声明 `Info.json.GameVersion` 的 | **0 个** |
| 资源站 API 是否有结构化的兼容字段 | **有**（见下方「重要更正」，2026-10-01 拿到官方 API 文档后修正） |

> UMM 界面里 Requirements 那一列全是 `-`，就是这个原因：
> **它不是"判断出兼容"，而是"没信息可判断"。**

### ⚠️ 重要更正（2026-10-01）

站长提供了官方 API 文档（<https://www.adofaitools.top/api/docs>），核对后发现：
**资源站其实有结构化的兼容字段**，只是我最初只看了顶层字段、看漏了它藏在版本的文件里：

```
GET /api/mods/{resourceType}/{slug}
  → versions[].files[].supportedGames[] = { name, version }
```

`version` 是**约束表达式**（不是自由文本），实测真实写法：

| 写法 | 例子 | 含义 |
|---|---|---|
| 比较符 | `>=3.4.0`、`==3.3.1`、`>3.4.0` | 大于等于 / 精确 / 大于 |
| 区间 | `[2.9.5,2.9.8]` | 闭区间 |
| 波浪区间 | `2.9.5~2.9.8` | 范围 |
| 裸写 | `3.4` | 通常表示同主次版本 |
| 修订号 | `>=r150`、`>r125` | 对应游戏内部修订号（如 3.4.0 的 r150） |

**填写率实测：121 个 mod 中有 5 个填了（约 4%）**，但填了的都很规范，例如：

- `AccurateJudgementBar`：`2.4.1` → `>=3.4.0`；`2.4.1-before-3.3.1-edition` → `==3.3.1`
- `CheryTools-Fable`：`26.5` → `>=3.4.0`；`26.4` → `>= 3.3.0`
- `Iridium`：`[2.9.5,2.9.8]` 与 `>=2.10.0`（同一版本列多个条件）

**结论修正**：这条路是**通的、而且是权威的**——作者填了就 100% 可信。
所以我之前说的"只能多来源聚合"，应改为：

> **优先用 `supportedGames`（结构化、作者填的）；没填的再靠自由文本 / 运行日志兜底。**

> 另外：工具条目也有同名字段 `versions[].supportedGameVersions`（字符串数组），
> 所以 AMM 自己在资源站上也可以声明"适配的游戏版本"。

资源站上**没填该字段**的 mod，其兼容信息仍以自由文本散落在几处：


- `description`：「如果你正在使用 ADOFAI 3.3.1 版本，请使用 AJB 2.4.1-before-340-edition 版本」
- 版本号本身：`2.4.1-before-340-edition`、`2.4.1-before-3.3.1-edition`
- 显示名：`AccurateJudgementBar (3.4.0 and 3.3.1)`

所以「自动判断」不能靠单一字段，只能**多来源聚合 + 标注可信度**。

## 2. 四类可用信号（按可信度排序）

| 层 | 来源 | 可信度 | 维护成本 | 能否提前判断 |
|---|---|---|---|---|
| **A** 元数据 | `Info.json.GameVersion` | 权威 | 0（等作者填） | ✅ 能（可惜几乎总是空） |
| **B** 运行日志 | `<Game>_Data\Managed\UnityModManager\Log.txt` | **最高（是事实）** | 0 | ❌ 只能事后 |
| **C** 作者声明 | GitHub Release 说明 / 站点更新说明 / 版本号 | 高（作者亲口） | 0 | ✅ 能 |
| **D** 启发式 | 更新时间、简介关键词 | 低 | 0 | ⚠️ 只能"疑似" |

### A. 元数据（保留现状）

作者若填了 `GameVersion`，按 UMM 的语义把它当作**最低游戏版本**：只有当前游戏版本低于它时才提示；游戏更新到更高版本不应误报。`ManagerVersion` 同理，用于检查最低 UMM 版本。

### B. UMM 运行日志 ⭐ **推荐主力**

UMM 每次运行游戏都会写一份日志（UTF-8，**每次覆盖**）。实测内容示例：

```
[Manager] FINISH. SUCCESSFUL LOADED 11/12 MODS.              ← 总体结果
[Manager] [Error] Id 'AccurateJudgementBar' already uses another mod.
                                                             ← 重复安装（UMM 自己报的）
[AccurateJudgementBar] Version '2.4.1'. Loading.
[AccurateJudgementBar] Active.                               ← 这个 mod 加载成功
[TogetherBootstrap] [Exception] OnToggle: NullReferenceException
                                                             ← 这个 mod 实际报错了
```

**优点**

- 是**事实**，不是猜测；不依赖作者写任何字段；
- 顺带能发现：**重复安装**、**加载失败**、**mod 抛异常**；
- 零维护。

**能做的产品形态**

1. 每个 mod 卡片标注：`上次运行 ✓ 加载成功` / `✗ 报错：NullReferenceException` / `— 还没跑过游戏`
2. 页面顶部一句话：`上次游戏运行（19:01）：11/12 加载成功`
3. **兼容性时间线**（增强）：每跑一次游戏就存一条极简记录（日期 / 游戏版本 / 各 mod 状态），
   于是当游戏更新后可以直接得出结论：
   > 「游戏更新到 3.4.0 之后，`CheryTools`、`TUFHelperLite` 开始报错」

**注意**：日志只说"上次运行"，所以定位是「**跑完告诉你真相**」。

### C. 作者声明（实测有料，但格式不统一）

**GitHub Release 说明**（实测例子）：

```
Creplay v2.15 : 适配adofai3.4.0（同时不再支持3.4.0之前的版本）。
Creplay v2.11 : 适配adofai 3.3.1(r148)并且不再支持以前的版本
AdofaiTweaks  : Mod is now up to date with v3.4.0. Enjoy
```

注意 Creplay 的写法连**兼容范围**都给出来了（"不再支持之前的版本"）。
而且 AMM 检查 GitHub 更新时**本来就会读到 Release 说明**（同一个请求，零额外开销）。

**资源站侧**：`versions[].versionId` 与显示名常带线索
（`2.4.1-before-340-edition`、`(3.4.0 and 3.3.1)`），部分 mod 的更新说明里也有。

**实测覆盖率（抽 4 个能定位到 GitHub 仓库的 mod）**

| mod | 最新 Release 说明里是否有适配版本 | 原文 |
|---|---|---|
| Creplay | ✅ | `适配adofai3.4.0（同时不再支持3.4.0之前的版本）` |
| AdofaiTweaks | ✅（英文写法） | `Mod is now up to date with v3.4.0. Enjoy` |
| AccurateJudgementBar | ➖ 写在站点简介/版本号里 | `2.4.1-before-340-edition` |
| ADOFAI.EditorTweaks | 未取到 | — |

> 结论：**有料，但格式散**。要做得靠谱，需要为"已知模式"写规则（中/英文常见句式），
> 并且明确标注为"作者声明"，而不是"系统判定"。

### D. 启发式（弱，谨慎）

- mod 最后更新时间 vs 游戏版本发布时间（"这个 mod 一年没更新了，游戏上个月大更新"）；
- 简介里出现版本号。

**只作灰色"疑似"提示，必须可一键关闭**，否则会变成误报骚扰。

## 3. 三条必须守住的原则

1. **「没写」≠「不兼容」**
   现在 0/11 声明了版本。如果按"不匹配就警告"，会满屏飘红，用户会直接不信任这个功能。
   未知就老实显示「未声明」。

2. **分级展示，不混为一谈**

   | 级别 | 依据 | 展示方式 |
   |---|---|---|
   | 确定 | 元数据 / 运行日志 / 作者明确声明 | 黄或红，说清依据 |
   | 疑似 | 启发式（更新时间等） | 灰字，可折叠 |
   | 未知 | 没信息 | 不显示 |

3. **绝不自动禁用或拦截 mod**
   只提示，决定权永远在用户手里。

## 4. 推荐路线

| 阶段 | 内容 | 说明 |
|---|---|---|
| **第一步** | **B 层（读 UMM 日志）** | 收益最大、零维护，还能顺带解决"重复安装/加载失败"的提示 |
| 第二步 | B 层 UI 改造 | 卡片加载状态 + 页面顶部总结 |
| 第三步 | **B 层 + 时间线** | 游戏更新后能自动指出"哪些 mod 开始坏" |
| 第四步 | **C 层（作者声明）** | 读 Release 说明/站点更新说明，用规则提取，标注来源 |
| 第五步 | 社区清单（可选） | 仓库里维护 `compatibility.json`，人工/PR 校正 |

> 我的建议：**先做 B**。它是唯一"不依赖任何人配合"就能给出可靠结论的来源，
> 而且顺带解决重复安装、加载失败这两类真实问题。
> C 层可以同步做轻量版（反正 Release 说明已经白拿）。

## 5. 给站长的建议（若能推动，是最彻底的解）

在资源站的 mod/版本上增加一个**可选的结构化字段**，例如：

```json
{
  "gameVersions": ["3.4.0"],          // 明确支持的版本
  // 或更精确的区间
  "minGameVersion": "3.4.0",
  "maxGameVersion": "3.4.0"
}
```

- 上架/更新版本时，表单里给一个**可选**输入框（不强制、可留空）；
- 一旦填了，**所有客户端（不只 AMM）都能 100% 准确判断**，不必再猜；
- 可与现有 `description` 互补：填了字段 = 确定，只写文字 = 客户端尽力解析。

这样"兼容性"就从"各家客户端各自瞎猜"变成了"**站点提供事实**"，对生态最有利。

## 6. 待定问题（需要一起拍板）

1. B 层（读日志）要不要做？会不会涉及隐私顾虑（日志里含本机路径）？
   - 说明：日志只在本机读取、不上传，且 AMM 已做同类本地化处理（配置/缓存都在用户目录）。
2. 时间线要存多久、存哪些字段？（我倾向：只存"日期 / 游戏版本 / 每个 mod 的成功或失败"，不存日志正文）
3. C 层用规则解析作者声明，**误报**怎么兜？我的建议：解析结果一律标注「来源：作者更新说明」，并允许用户一键忽略。
4. 要不要引导作者填 `Info.json.GameVersion`？（可以在 mod 详情页放一句提示 + 科普）
5. 是否推动站长加结构化字段（见第 5 节）？这件事的收益远大于客户端侧的启发式。

## 附：实测可解析的规则样例

```text
# UMM 日志
[Manager] FINISH\. SUCCESSFUL LOADED (\d+)/(\d+) MODS\.
\[Manager\] \[Error\] Id '([^']+)' already uses another mod\.
^\[(?<id>[^\]]+)\] Version '(?<ver>[^']*)'\. Loading\.
^\[(?<id>[^\]]+)\] Active\.$
^\[(?<id>[^\]]+)\] \[(Exception|Error|Warning)\] (?<msg>.+)$

# 作者声明（Release 说明 / 站点更新说明）
适配\s*(?:adofai|ADOFAI)?\s*v?([0-9]+\.[0-9]+(?:\.[0-9]+)?)
不再支持\s*([0-9]+\.[0-9]+(?:\.[0-9]+)?)?\s*之前的版本
(?:up to date with|supports?|requires?)\s*v?([0-9]+\.[0-9]+(?:\.[0-9]+)?)
版本号：(?:^|[-_])before-([0-9]{3})-edition     # 2.4.1-before-340-edition => 3.4.0
```
